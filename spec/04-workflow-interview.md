# Workflow interview

These questions map how a real MSP network tech works, so the game's steps, choices and scoring match reality. All 50 were answered in chat on Oct 16 and 17, 2026 by a working MSP network admin. Each answer shaped a section of the main spec. When the spec and these answers disagree, these answers win.

| # | Area | Question | Answer |
| --- | --- | --- | --- |
| 1 | Intake | When a network ticket lands in your queue, what are the first three things you read or check before touching anything? | Read title and description; confirm priority fits the urgency. Look up the client environment in docs: servers, VPN needed, switches. If config backups exist in docs, review them first to understand the gear. If urgent, skip review and start troubleshooting immediately. |
| 2 | Intake | Who sets priority (dispatch, tier 1, you), and can you change it? | Level 1 and 2 techs can set priority 2 through 4. Only dispatch sets P1: someone reviews the ticket, decides it's P1, messages dispatch, and dispatch coordinates the team and assigns the right resource based on workload. Dispatch checks in with the tech at intervals; most P1s need a check-in every hour until de-escalated. |
| 3 | Intake | What does a tier 1 escalation usually contain, and what is usually missing? | Usually: user name, location, vague general details. Missing: screenshot of the exact error, exact site or app name, phone MAC, IP address. Tech cross-references the username in RMM to find their machine, then runs a ping test or LLDP scan from it to learn which switch port or AP they're on. |
| 4 | Intake | What makes you send a ticket back to tier 1 or dispatch instead of working it? | Wrong ticket category is the big one: something sent to the network team really belongs to security or general engineering. Example: an endpoint security console (FortiClient EMS in real life) is a security tool with no direct interaction with the firewall, but gets assigned to a network tech by mistake; once they find they don't have access to that system, they tell dispatch to redistribute it. Also: complete lack of information, nothing to go on. |
| 5 | Intake | How do you handle several tickets or alerts for the same outage? | Dispatch merges tickets. The tech reviews them, determines they're duplicates, and tells dispatch. |
| 6 | Monitoring | Which alerts do you act on right away, and which wait until a ticket exists? | Act right away on: firewall offline, a CVE scored 9.0 or higher, a whole group of devices offline (e.g. an entire classroom). |
| 7 | Monitoring | What does a false alarm usually look like, and how do you prove it is false? | Symptom-only reports. A monitoring probe goes offline, so the whole network is reported down. A user reports no internet but is just disconnected from Wi-Fi or Ethernet. |
| 8 | Access | Getting into a client firewall from home: what do you open, in order? | Most client servers and boxes can be reached through RMM. Workstations too, but never without the user's consent. Some clients prefer you connect to the VPN and manage the firewall at its local interface address, or through a central firewall management tool. Some network tools are reached directly in the cloud (cloud-managed AP, switch and gateway dashboards). |
| 9 | Access | When the credentials in docs are wrong, what is your next move? | Try older versions in the docs history tab. Try vendor defaults. Call the last person who viewed the entry in the docs tool, or call the client for credentials. Some clients disable MSP accounts when there's no open ticket or project. |
| 10 | Access | When do you pick the RMM agent vs VPN vs a one-time session? | Check documentation first: do they have a server, cloud-managed network devices, VPN, or are they a one-time remote session client? The docs decide the path. |
| 11 | Access | What do you do when every remote path is down? | Call the client and troubleshoot through them as remote hands and eyes. Old-school troubleshooting. |
| 12 | Investigation | Whole site down: what do you check first, second, third? | Look up the firewall in docs; if static WAN IP, ping it. No response: contact ISP. In RMM, filter workstations by the firewall's public IP to see what's online or offline and when they dropped (remote workers show home IPs, ignore them). ISP may say equipment is online: have client power cycle the modem or read status lights. Causes seen: ISP outage, failed provisioning update (ISP reboots it), cable unplugged at the firewall. If ISP outage with no failover: tell client they must wait, we monitor via firewall status reporting, and ask them to tell us when internet is back so we can verify everything. |
| 13 | Investigation | One user can't connect: your order of checks? | Online or offline? Can they ping local devices, ping the gateway, is DNS working? Static IP set, VPN connected, duplicate firewalls or IPs, wrong website name, or wrong file share path. |
| 14 | Investigation | Wi-Fi complaint: what do you look at first in the controller? | Listen and correlate. Ask: which Wi-Fi network are they on, how much signal, do they have line of sight to the AP, when did they last reboot? In the dashboard: ISP latency, client latency, number of clients, signal strength. |
| 15 | Investigation | Site-to-site tunnel down: first three things? | Check both sides. Did the WAN IP change at either location? Toggle or bounce the tunnel and see if it returns. If not, read the logs for the exact error: pre-shared key changed, remote selector changed, or a local network IP range changed. |
| 16 | Investigation | Which logs and tools do you trust, and which do you second-guess? | Second-guess most: the network monitoring tool. SNMP setup is tricky on some devices and not fully reliable; inventory can be stale (wrong IPs, inconsistent port mapping). Useful for inventory and alert history, not absolute truth. The RMM: very reliable for data on connected machines. Cloud firewall consoles and switch suites: very reliable, but configs can be hard to read; downloading the config and reviewing locally is often faster. Direct SSH or web GUI on the device: most absolute. Any alert via ticket, email or client should be verified and cross-referenced first. |
| 17 | Investigation | When do you call the client contact vs work quietly in the background? | Call directly whenever it will get me across the finish line right away, or for a quick answer or a quick test, to skip the dispatch scheduling loop. Depends on the business: some clients don't like direct calls at all and only want to be scheduled at their leisure. |
| 18 | Dispatch | What does a status update to dispatch look like: fields, wording, length? | Short and outcome-based. Resolved: say so and close. Otherwise tell dispatch which path: reschedule to next available block (note if client must be present), Teams call with client, after-hours maintenance (give general days and times I'm available), sales, customer question, or new ticket for a separate issue found. New tickets land back in my queue. |
| 19 | Dispatch | What ticket statuses exist in your PSA, and when do you set each? | Awaiting Client Response, Feedback Received, Dispatch Review, Scheduled, Closed, and Follow-up Needed (set on tickets with no status update for 3 days). |
| 20 | Dispatch | What do you never say or promise directly to a client? | Never promise a timeline. Never promise anything when you're not the one doing the work, including what another team member will do, unless they verbatim told you that you can tell the client. Training requests: not what we do; won't spend time, even billable, training someone unless it directly affects their daily operations. |
| 21 | Dispatch | How does dispatch tell you a window or visit is booked? | Dispatch books the block on my calendar. For P1s, dispatch reaches out, reschedules my existing items, and emails affected clients that work moved and I'll follow up. |
| 22 | Escalation | When do you escalate to a senior engineer, a vendor, or the ISP? | Senior tech gets involved when a client is too complex, e.g. a BGP issue, or multiple subnets on the same switch with no VLANs. Failed hardware can be a reason to escalate when the site is down. |
| 23 | Escalation | What do you gather before calling the ISP or opening a vendor case? | ISP: account number and security PIN; if not in docs, get them from the client's bill. Dead hardware: confirm it's dead, open a vendor case, RMA issued, replacement overnighted. Confirm delivery contact and address and give shipping details to the client. Return the old unit; expense return shipping and any onsite mileage. Clients who can't wait a day must request accommodation; those clients should have an HA pair, which is a sales issue, except cheaper or poorly funded clients. |
| 24 | Escalation | How long do you work something before escalating? | Depends: how close to resolution, is there a diagnosis, a recommended fix, a roadblock? No roadblock, just a lot of work: tell the team what you're working on in case they have input. Roadblocked: escalate as soon as you know you can't proceed in a reasonable time; no sooner than about 30 minutes, but you should know you're blocked well before then. Most tickets: after an hour without good progress, do some kind of check-in. |
| 25 | Change control | Which changes need client approval or an after-hours window? | Needs coordination: reboots, firmware updates, and any config change that affects availability of working gear. Tech often doesn't know the client's real business hours or who works late, so the client must be told to warn their team. No approval needed when it's already down (P1 or critical) or already broken, e.g. replacing an expired VPN certificate on the firewall. |
| 26 | Change control | Before an after-hours change, what prep do you do (backup, rollback plan, notice)? | Rollback plan, config backup, firmware pre-downloaded to the jump box or local machine. Check the upgrade path: if several versions behind, step through approved versions before a big jump. Read known issues: deprecated features can drop config, and VPN, DNS, SIP helper, or memory behavior can change (low-RAM firewalls can hit conserve mode and need proxy policies moved to flow). |
| 27 | Change control | A change goes wrong at 11 PM: what happens next? | Ideally the device boots its backup image automatically. If not, console cable. Worst case: onsite the next morning. Most common reality is a long wait after the update where you can't tell if it's broken or just slow, until it finally responds and traffic flows. The game should portray that suspense. |
| 28 | Onsite | What is in your bag when you go onsite? | Cable tester with remote IDs, toner and probe, RJ45 crimp tool, keystone and phone block punch tool, RJ45 ends, spare keystone jacks, faceplates, blanks, patch cords in various lengths, console cables for every equipment type (USB-C, micro USB, standard rollover, firewall-vendor console cable), laptop, small precision screwdriver set, label maker, utility knife, zip ties. |
| 29 | Onsite | First thing you do when you walk in, and who do you talk to? | Most facilities are locked: get buzzed in, check in with reception or meet the ticket's point of contact, who usually escorts you (or go yourself if you know the way). Floor plans are rare, and never show network gear. Discovered layout and equipment locations get saved to docs and the asset inventory, which is essential for directing smart hands, vendors or clients later. Contacts vary: some work almost on their own, others get frustrated and can't find things. Know where the bathroom is, don't get locked out; multiple buildings, floors and locked stairwells; room names, numbers, floors. |
| 30 | Onsite | What are you not allowed to do onsite? | Allowed: running cable, terminating jacks and RJ45 ends, trace and tone, cable testing, working on client-owned gear as long as it relates to the job. Off-limits: unannounced reboots. |
| 31 | Supported gear | What makes a device unsupported at your MSP? | Unmanaged devices are not recommended. Legacy gear without management interface access is bad for remote troubleshooting. Heavily mixed AP and switch vendors is generally bad, though doable if not too mixed. |
| 32 | Supported gear | Do you band-aid unsupported gear until it's replaced, or refuse to touch it? | Schedule the client to be onsite to help connect and reset it, or go onsite and reset it. Sometimes it gets replaced, depending on budget. Wealthier clients have better gear and infrastructure; nonprofits and scrappy clients are the hardest. |
| 33 | Supported gear | How do you raise it to sales, and what does that note include? | Example note: unmanaged device, unable to configure for networking needs; need a managed switch with a 3 or 5 year support contract for RMA and support. Usually recommend a managed device from the same brand they already have, or one sized to the client. |
| 34 | Supported gear | What do clients usually push back on when told to replace something? | They need a reason, and often ask if there's a workaround. Unmanaged isn't the end of the world, but it's usually not allowed for core or access switches. |
| 35 | Replacement | Swapping a firewall: your steps from config pull to cutover? | Document the old config: what each port does, VLANs, PoE, ISP settings, DHCP, static addresses. Power up the new device, update to matching firmware, restore config; if ports are the same, done. Different make or model: enter all settings by hand on latest stable firmware (check release notes); beta or bleeding-edge firmware means unstable devices. Verify every connected device is online: switches, APs, printers, phones. |
| 36 | Replacement | Swapping a switch: how do you handle port mapping and VLANs? | If the old switch works: read its config for VLANs, PoE settings, edge vs infrastructure ports, spanning tree and the rest. If it's dead with no config backup: check nearby equipment for which ports were trunks and what traffic they carry, maybe packet capture. Long after the fact or a single switch: put everything on the default VLAN and see what devices call out to, e.g. an unmanaged-but-configured switch sending a tagged VLAN over a trunk, or phones calling a PBX on a different VLAN. Port location matters: some switches have partial PoE, so label what's on the PoE side. |
| 37 | Replacement | What usually goes wrong on cutover night? | Wrong subnet mask. DNS not updated after the domain DNS server was retired in an AD to Azure AD (Entra) migration. ISP gear holding the old firewall MAC. Site-to-site tunnel missing, so one location can't reach the print server and can't print. Without VPN or a jump box, clients must leave machines on overnight: back up power settings via PowerShell, set always-on until done. |
| 38 | Replacement | What is on your post-install checklist? | Usually not a network admin's job; whoever delegates it has a checklist for how they like things set up. In the ticket: the task, the expected output, what actually happened, everything done along the way, so there's no question what was done. Permanent infrastructure (new device, new switch) goes into documentation. Sometimes a knowledge base article, e.g. how a client's authentication works and how to troubleshoot it. |
| 39 | Closing | What must a resolution note contain? | A statement of the issue, so it's clear you understood the problem (or at least a description of it); what you found while reviewing; any changes you made; next steps, if any; whether it's resolved; the root cause. |
| 40 | Closing | Which docs do you update after a fix? | Order: missing labels, then documentation, then the ticket, then tell the client. Only document what relates to the device worked on. Example: labeled both ends of the Ethernet runs for the APs and the APs themselves (not every cable) and updated the port map. Photos and network diagrams are done on new installs or network refreshes. |
| 41 | Closing | Does the client confirm before close, and how long do you wait? | Client-reported: close only if you tested with them (phone, email, any way) and have concrete proof you can screenshot or document in the ticket. Otherwise ask them if it's good to close. Exception: tickets you opened yourself because you found something can be closed without client interaction once you have proof it's resolved. |
| 42 | Closing | How do you log time: per step, per ticket, rounded? | Work in blocks, not overly granular. Don't log the moment it's fixed: review docs and configs, understand the setup, then close. Draft the client email while taking notes so sending it logs all the time. After a change that affects VLANs across firewall and switches, back up all connected equipment. Travel time is logged against the ticket, with a description of to or from the office. |
| 43 | Contracts | Managed vs break-fix client: what changes in how you work? | Break-fix clients have more problems but only want show stoppers fixed. Managed clients start with basic docs from onboarding; time-and-materials clients have nothing unless you add it. Break-fix clients must provide access, and how long depends on how hard the issue is. Always more grace with managed clients. Break-fix clients are more likely to become managed with each success. |
| 44 | Contracts | What SLA tiers exist, and how do they shape your day? | Industry standard tiers, with some leeway. A ticket becomes P1 if enough people are out of business or can't work, if a site is down in a major way, or if the ticket is too old with no action or client communication. |
| 45 | Contracts | How do project work and support tickets differ for you? | Projects aren't a mainstay for network admins. Tasks within a project get delegated and arrive as tickets marked as project work. Handled the same way, but the scope differs: new features you normally wouldn't do, e.g. setting up an IPsec VPN for remote users, or enabling SSO login with Microsoft 365 on the firewall. Projects are new features; normal tickets are break-fix. |
| 46 | Consequences | What gets a tech in trouble? | Rebooting equipment or making config changes without permission. Some clients have formal change control policies; others let you work on your own as long as nothing breaks. Not working tickets or taking too long can be an issue, but people are generally gracious if they know you're working on it. Fairly lenient for network techs overall. |
| 47 | Consequences | Worst incident you've seen, anonymized, and how it played out? | A client so lost they couldn't navigate to the one-time remote support site. One client said they had "Mozzarella Firebox" instead of Mozilla Firefox. |
| 48 | Day in the life | What does a typical shift look like, hour by hour? | Clock in, review emails, review tickets, decide if anything needs adjusting (L1 and L2 triage network tickets as they come in; network admin gets escalations). Check each calendar meeting: remote, client-facing, or onsite? Onsite: enough travel padding? Network review tickets: time budget too short or too long? After hours: ideally after 8 PM, can be any time after 5 PM for most businesses; critical clients (e.g. a police department) may need downtime at 3 AM. |
| 49 | Day in the life | How many tickets do you juggle at once, and how do you pick the next one? | About 6 in-depth tickets on a busy day. Network admin work is driven by the calendar, not the queue. Queue is checked so SLAs don't sneak up when I have to switch gears fast. |
| 50 | Day in the life | What is most satisfying and most annoying? What should the game reward or punish? | Tech happiness is tracked with a feedback tool (Crewhu in real life): good client feedback earns bonus points that can be redeemed to buy things. |

## Follow-up answers (Oct 17, 2026)

| Topic | Answer |
| --- | --- |
| On-call | A NOC exists but mostly covers servers. Network calls and alerts after hours go to an on-call rotation. |
| Quarterly network review | An overall look at the network: device licensing and support status, devices offline, configuration issues, security risks such as CVEs against current firmware, loops, speed and negotiation problems on trunks, glaring mistakes like a guest network on VLAN 1 with the corporate network, critical firmware updates (minor ones skipped unless needed), and updating docs with anything missing such as switches and APs. |
| Offboarding | VPN access is about the only network piece. Tier 1 and 2 handle it, since they get the employee separation and termination tickets from clients. |
| Seasons | Back to school is busy. End of year is usually quiet around Christmas. Tax time is busy for accountants and similar offices. Otherwise follow each industry's activity trends. |
| Starting role | The player starts as an MSP engineer recently promoted to network admin. Other tiers could come later; the focus is networking. |
| Proposed items | Every proposed item in the spec was kept. Documentation matters most: docs and KB articles let tier 1 and 2 handle more on their own (for example, a guide on allowing a website through the web filter, or VPN user onboarding steps), which cuts escalations to the network admin. |
| Tooling | Ticketing, RMM, remote sessions, help desk and monitoring merge into one all-in-one platform (Atrium, an Atera look-alike). Each module keeps its own name as a landing page inside Atrium. VPN clients, SSH and terminal tools, and console cables stay separate. |
